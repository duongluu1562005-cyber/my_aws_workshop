RUNTIME, SEEDING AND EDGE

Connect the deployed stacks into a running Tindy environment. Edge provides the HTTPS hostname. Runtime runs the API behind CloudFront VPC Origin and an internal ALB. Database tasks prepare DB roles, schema and demo data before enabling the API.

Keep Edge in maintenance and Runtime at DesiredCount 0 while preparing secrets, bootstrap, migrations and seed data. Open traffic after successful DB tasks and API health checks.

5.5.1 — Create Edge in maintenance mode

Create edge.yaml first to obtain DistributionDomainName, used as Runtime CloudFrontPublicHost and for OAuth callback updates during authentication verification.

ComponentPurpose
CloudFront distributionProvides the HTTPS entry point for frontend and API.
Origin Access ControlEnables CloudFront access to the frontend S3 origin through its bucket policy.
Frontend bucket policyRestricts origin access to the configured distribution.
Maintenance routing functionReturns HTTP 503 and maintenance JSON for API routes while the backend is being prepared.

Initially use EdgeMode = maintenance and leave AlbDnsName and VpcOriginId empty. Switch to live with the new Runtime values after the API becomes healthy.

Expected result is CREATE_COMPLETE, three Outputs and HTTPS /api/health/ready returning HTTP 503 with maintenance JSON.

5.5.2 — Create Runtime with DesiredCount zero

runtime.yaml consumes inputs from Foundation, Network, Database, Integrations and Edge.

Resource groupPurpose
ECS cluster, task definition and serviceDefine the image, configuration, secret references, CPU/memory and task count.
Execution and task IAM rolesSupport container startup and application AWS access.
Internal ALB, listener and target groupReceive VPC Origin traffic, route requests to the container and check health.
CloudFront VPC OriginConnects the distribution to the internal ALB.
Security group ingressRestricts ALB access according to CloudFront configuration.
CloudWatch log groupRecords API and database task logs.
Conditional one-off task definitionsRun bootstrap, migrations and seeding once required parameters are supplied.

Create Runtime with a digest-pinned image, DBProvisionMode = Fresh and DesiredCount = 0. Retain the verified OAuth, media and Bedrock text settings. Keep AI PDF false during schema preparation. Once the zero-count service exists, prepare secrets and update parameters to enable DB tasks.

Stages after Runtime creation

OrderWorkVerification
1Prepare application/migration/seed secrets and verify the new endpoint.Secret references match the Fresh DB configuration.
2Add one-off task inputs through a change set.Bootstrap, migration and seed definitions appear in Outputs.
3Run bootstrap → migrations → seed sequentially.Each task exits with code 0 and completion logs.
4Configure CloudFront service SG ingress and set DesiredCount to 1.Stable ECS service and Healthy target group.
5Update alarm dimensions and switch Edge live.API readiness returns 200 through the new hostname.
6Update OAuth, release frontend and verify demonstration flows.Frontend and API work through CloudFront.

Each stage will receive detailed instructions and screenshots as it is performed. API and migration credentials serve separate DB roles, while the master secret supports bootstrap.
